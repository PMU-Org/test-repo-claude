# WebM → HTML5 Banner

Конвертер відео-креативів `.webm` у самодостатній HTML5-баннер. Працює повністю
в браузері: файл нікуди не завантажується, серверної частини немає — тому
інструмент і живе на GitHub Pages як статична сторінка.

**Живий тул:** https://pmu-org.github.io/test-repo-claude/ ·
**приклад збірки:** https://pmu-org.github.io/test-repo-claude/demo/ ·
**версія в один файл:** [`dist/converter-standalone.html`](dist/converter-standalone.html)

## Що робить

| Крок | Деталі |
| --- | --- |
| Розбір відео | `<video>` + покадровий `seek` у `<canvas>`; VP8/VP9, альфа-канал зберігається |
| Визначення fps | вимірює інтервали між реально показаними кадрами (`requestVideoFrameCallback`) і прив'язує до стандартної частоти |
| Спрайт-аркуш | сітка, близька до квадрата, до 16 383 px по стороні; WebP / PNG / JPEG |
| Баннер | `<meta name="ad.size">`, глобальний `clickTag`, анімація `background-position` |
| Пакування | ZIP для Google Ads / DV360 / Campaign Manager — типово одним самодостатнім `index.html` |
| Профілі майданчиків | дозволені типи файлів, ліміт ваги, кількість файлів і довжина анімації — з перевіркою пакета |
| Автопідбір | шукає роздільність, fps і якість під ліміт обраного профілю |

Плеєр у згенерованому баннері рахує час накопиченням у `requestAnimationFrame`,
тому не «пливе» на потрібній частоті, ставиться на паузу на невидимій вкладці й
зупиняється на останньому кадрі, коли ліміт повторів витрачено — те, що
вимагають IAB і Google Ads від display-креативів.

## Профілі майданчиків

Майданчики розходяться не в дрібницях, а в базовому: як зветься точка входу, чи
можна складати ассети в один файл, які формати зображень приймаються. Профіль
задає це все і перевіряє готовий пакет.

| Профіль | Точка входу | Формати | Вага | Ассети | Клік |
| --- | --- | --- | --- | --- | --- |
| **Admixer Standard HTML5** | `body.html` у корені | JPG / PNG | 300 КБ | тільки окремими файлами | `globalHTML5Api.click()` |
| Google Ads — uploaded display | `index.html` | JPG / PNG | 600 КБ | на вибір | `clickTag` |
| Display & Video 360 / CM360 | `index.html` | JPG / PNG | без жорсткого ліміту | на вибір | `clickTag` |
| IAB LEAN | `index.html` | будь-які | 150 КБ | на вибір | `clickTag` |

WebP немає в дозволених типах ні в Admixer, ні в Google, ні в DV360 — тому
типовий формат спрайта JPEG. Результат показує пас/фейл по кожному пункту,
блокуючі позначені явно.

### Що саме робить профіль Admixer інакше

- **`body.html`**, не `index.html` — і в корені архіву, без вкладених тек.
- **Стилі й креатив усередині `<body>`.** Документація Admixer прямо каже
  давати розмітку в межах `<body>`, інакше банер може не показатись — тому
  `<style>` переїжджає в тіло документа, а не лишається в `<head>`.
- **Старт на `globalHTML5Api.on('load', …)`** замість самостійного запуску.
- **Клік через `globalHTML5Api.click()`** без аргумента: URL береться з поля
  Landing Page в шаблоні креатива. Передати URL у коді можна галочкою «URL у
  коді креатива», але тоді поле в UI треба залишити порожнім — Admixer вважає
  URL в обох місцях конфліктом, і код має вищий приоритет.
- **Без `README.txt` в архіві** — `.txt` немає в переліку дозволених типів, та
  й 300 КБ не та вага, щоб витрачати її на документацію.
- **Ассети тільки окремими файлами** — вибір пакування для цього профілю
  заблокований, спрайт у `data:` URI там не приймуть.

Якщо API немає (банер відкрили подвійним кліком), креатив це помічає, стартує
сам і відкриває URL напряму — тобто експорт лишається придатним до перегляду.

## Головний компроміс

Спрайтовий баннер важить лінійно від кількості кадрів. Для фотографічного
креативу 300×600 × 2 с бюджет 150 КБ означає вибір: **різкість або плавність**.
Перемикач «чим жертвувати першим» задає, що автопідбір ріже раніше:

- **Тримати різкість** (типово) — спрайт залишається 1:1, падає fps.
  Обов'язково для креативів з дрібним юридичним текстом: на 75%
  роздільності дисклеймер уже нерозбірливий.
- **Тримати плавність** — fps зберігається, спрайт кодується в 85…50%
  роздільності й розтягується засобами CSS.

## Пакування та «відкриваю банер, а там біле»

Спрайт окремим файлом — вимога Admixer і багатьох інших майданчиків, але саме
через неї банер найчастіше показує пусто. Windows Explorer при відкритті файлу
прямо з архіву розпаковує **тільки його**, сусідній `sprite.jpg` лишається в
ZIP, картинка не вантажиться — і банер малює білий прямокутник без натяку на
причину.

Тому в режимі окремих ассетів банер більше не молчить: якщо спрайт не
завантажився, він пише, якого файлу бракує і що зробити. Тільки під `file://`
та localhost — щоб реальний глядач реклами ніколи не побачив діагностику.
Де майданчик не наполягає на окремих файлах, доступне пакування «спрайт
усередині HTML»: один файл, який частковою розпаковкою не зламати, ціною ~33%
ваги на base64.

Приклад із `demo/` під профіль Admixer: джерело 1538 КБ, 30 fps → **292 КБ
ZIP** (`body.html` + `sprite.jpg`), 20 кадрів @ 10 fps, спрайт 2100×1800 у
масштабі 1:1. Той самий
креатив у жорсткі 150 КБ (IAB LEAN) тисне до 16 кадрів @ 8 fps і якості 26 —
різниця між реальним лімітом майданчика і «про всяк випадок 150 КБ» тут
коштує половини частоти кадрів.

## Один файл, без сервера

[`dist/converter-standalone.html`](dist/converter-standalone.html) — той самий
конвертер, зібраний в один файл: CSS і всі модулі інлайном. ES-модулі не
вантажаться через `file://`, тому многофайлова версія вимагає http-сервера, а ця
відкривається подвійним кліком — зручно, коли креатив не має покидати ноутбук.

## Локальний запуск

```bash
npm run serve          # http://localhost:8080 — потрібен http(s), не file://
npm run build:demo     # перезбирає demo/ у headless Chromium; це ж і e2e-тест
npm run build:single   # перезбирає dist/converter-standalone.html
```

`build:demo` проганяє повний шлях — зразок → автопідбір → ZIP → перевірка, що
баннер справді анімується, віддає правильний `ad.size`, має `clickTag` і
розкладається точно в заявлений розмір. Падає, якщо щось із цього зламано.

## Структура

```
index.html              конвертер
assets/js/extract.js    зняття кадрів з відео
assets/js/sprite.js     пакування та кодування спрайта
assets/js/banner.js     генератор HTML-баннера і README пакета
assets/js/zip.js        ZIP-writer (store-only, власний CRC32)
assets/js/app.js        UI, автопідбір під бюджет
tools/build-demo.mjs    e2e-тест і генератор demo/
tools/build-single.mjs  збірка версії в один файл
```

ZIP пишеться без DEFLATE: усе, що в нього кладеться, вже стиснуте (WebP/PNG/JPEG),
тож компресія дала б одиниці відсотків, а залежність від zip-бібліотеки лишилася б.

## Обмеження

- Потрібен браузер, що декодує вхідний кодек: Chrome 94+, Edge, Firefox 100+,
  Safari 16.4+. Safari не декодує VP9 з альфою — там прозорість буде втрачена.
- Backup-зображення не входить у ZIP: усі згадані платформи приймають його
  окремим файлом, а в пакеті воно лише з'їдало б бюджет 150 КБ.
- Кліпи довше ~5 с у 150 КБ не вкладаються — ріжіть анімацію або підіймайте бюджет.

## Деплой на GitHub Pages

`.github/workflows/deploy-pages.yml` публікує корінь репозиторію як є — без
кроку збірки, бо сайт це статичні файли. Тригериться пушем у default-бранч
і вручну через **Run workflow**.

Pages у цьому репозиторії вже увімкнено (**Settings → Pages → Source: GitHub
Actions**). Якщо форкнути репо, це доведеться зробити ще раз руками:
воркфлоу не вміє увімкнути Pages сам, бо REST-ендпоінт *Create a GitHub Pages
site* вимагає **admin**-прав, а `GITHUB_TOKEN` вище `write` не піднімається —
незалежно від видимості репозиторію. Без цього перший крок падає на
`Create Pages site failed. Error: Resource not accessible by integration`.
